Notion guided setup writes these values to the ignored `.dev.vars` file. Keep the generated values; the examples below are placeholders.

```dotenv title=".dev.vars"
NOTION_TOKEN=replace_with_your_internal_integration_token
FEEDBAX_API_KEY_HASH=replace_with_the_generated_sha256_hash
PARTICIPATION_SIGNING_SECRET=replace_with_the_generated_signing_secret
# Required only for Connected Profile (same secret on the product server):
IDENTITY_HANDOFF_SECRET=replace_with_an_independent_random_handoff_secret
# Required only when turnstile.enabled is true:
TURNSTILE_SECRET_KEY=replace_with_your_turnstile_secret
```

`src/feedbax.ts` contains public product settings, independent capability switches, Notion identifiers and stable property IDs, the optional Connected issuer/login URL, and the public Turnstile site key. It contains no Notion token, API key, API-key hash, Turnstile secret, participation signing secret, or identity handoff secret.

`feedbax deploy` uploads only the allowlisted secrets to Cloudflare's encrypted secret store after showing the target and receiving confirmation. It never uploads arbitrary local environment values.

The trusted submission key printed by the creator belongs in the **calling product's server environment**. The copied server helper calls that value `FEEDBAX_API_SECRET`; the portal stores only its hash as `FEEDBAX_API_KEY_HASH`. Never expose the plaintext key to browser code.

Rotating `PARTICIPATION_SIGNING_SECRET` invalidates outstanding Participation Passes and Comment Capabilities. `feedbax rotate-api-key` rotates the trusted submission key and synchronizes its local hash; update the calling product with the newly printed key.

For Connected Profile, add the dedicated `FEEDBAX_DB` D1 binding to Wrangler configuration and apply its migration. The binding is infrastructure configuration, not a plaintext secret. See the [complete authentication guide](/docs/guides/connected-profile) for application setup, secrets, sessions, verification, and troubleshooting.

## GitHub secrets in 0.2.2 development

A GitHub portal uses `GITHUB_PAIRING_SECRET`, `FEEDBAX_API_KEY_HASH` and `PARTICIPATION_SIGNING_SECRET`, plus independently enabled Turnstile/Connected/email secrets. It needs no `NOTION_TOKEN`. Pairing stores separate portal-to-service and service-to-portal credentials in its private D1 database. Keep the bootstrap secret private and use the pairing flow for rotation/reconnection.

Only the integration service holds `GITHUB_APP_ID`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GITHUB_APP_PRIVATE_KEY`, `GITHUB_WEBHOOK_SECRET` and its independent `INTEGRATION_SIGNING_SECRET`. A portal never receives the App key. The [service README](https://github.com/jessequartey/feedbax/blob/main/apps/github-integration/README.md) covers registration and deployment.

Keep private identifiers and secrets out of public build variables. GitHub client assets/source maps are checked against configuration sentinels during packed-package validation. App callback URLs and raw webhook bodies must stay out of routine logs and exported diagnostics.
