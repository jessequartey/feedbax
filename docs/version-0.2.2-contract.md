# Version 0.2.2 shared implementation contract

Status: design target with an owner-accepted implemented release cut for 0.2.2. See the [accepted inventory and evidence](version-0.2.2-acceptance.md#accepted-release-cut); Projects and unfinished lifecycle work carry forward without delivery claims.
Owner decisions: 2026-10-15. Requirements: [release plan and amendments](version-0.2.2-plan.md).

## Released baseline and precedence

Production acceptance for 0.2.1 passed on Workers Free. Tag `v0.2.1` points to `371d18e`, and both `feedbax@0.2.1` and `create-feedbax@0.2.1` were verified in npm on 2026-10-15. The [GitHub release](https://github.com/jessequartey/feedbax/releases/tag/v0.2.1) was published at 07:09:33 UTC. The earlier pending-release wording in the acceptance record is historical, not a new implementation gate. This contract does not advance package versions or authorize a 0.2.2 publication.

The dated owner amendments override the original release handoff. Existing Notion behavior is the compatibility baseline. New GitHub behavior belongs behind the Feedback module's storage and Comment seams; the Changelog module remains separate. New Team Member tools and capabilities that require them remain deferred under ADR-0036. A deferred action is unavailable rather than authorized through a weaker path.

## Capability combinations

| Content Provider | Operational storage       | Participant identity                | Supported contract                                                                                                                                  |
| ---------------- | ------------------------- | ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Notion           | None                      | Browser capabilities/Device Profile | Existing Notion-only behavior; best-effort participation; no reliable unique Votes, My feedback, Follows, Notifications, or authenticated uploads   |
| Notion           | Explicitly provisioned D1 | No Identity Handoff                 | Only explicitly enabled operational capabilities; no implicit verified participation or cross-device ownership                                      |
| Notion           | Explicitly provisioned D1 | Signed Identity Handoff             | Connected Profile; existing features retain independent opt-outs                                                                                    |
| GitHub           | None                      | Any                                 | Reject configuration with an actionable D1 provisioning error                                                                                       |
| GitHub           | Explicitly provisioned D1 | No Identity Handoff                 | Browsing, submission, browser-authorized drafts, native publication and explicitly best-effort Votes/Comments; no verified participation guarantees |
| GitHub           | Explicitly provisioned D1 | Signed Identity Handoff             | Connected Profile, with enabled Votes, portal Comments, Follows, Notifications, My feedback, and private R2 uploads                                 |

GitHub best-effort Votes/Comments use Feedbax browser capabilities and private D1 operational records, not GitHub reactions or Participant GitHub accounts. They retain the existing Device Profile/rate-limit/capability rules without asserting unique identity or cross-device continuity. Existing Notion best-effort behavior is unchanged. D1 availability alone grants neither identity nor reliable social features. Do not silently provision D1/R2/Queues when upgrading a Notion-only Installation. R2, email, and scheduled processing are required only for their enabled capabilities. Feature incompatibilities fail at setup/startup with repair instructions.

Provider selection is a closed Notion/GitHub choice, not a plugin registry. Existing configuration without a provider discriminator resolves to Notion. New GitHub configuration contains only the selected provider's public identifiers and policy; secrets live in ignored local or encrypted deployment configuration. GitHub-only setup rejects enabled Changelog with instructions to disable it and does not request Notion credentials. Notion Changelog and feature opt-outs retain their released contract.

## Identity and authoritative data

One Installation serves one Product Team and product. Its stable identifier is generated during setup and bound to its portal origin. A GitHub App installation ID is a separate external identity and may serve multiple Portal Bindings. One Feedback Repository belongs to one active Feedbax writer binding at a time; development repositories may be shared only through explicit, separately verified permissions.

| Data                                                                     | Authority and visibility                                                                                                                                                          |
| ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stable Post identity, immutable public slug, provider references         | Preserve existing Notion IDs/slugs; new GitHub Posts get stable Feedbax identity and private D1 mappings to repository/issue IDs; slugs never change on title edits or migration  |
| Post content, six Post Status values, publication, concise Team Response | Selected provider; GitHub uses a versioned explicit public-content section plus the configured workflow authority                                                                 |
| Verified Participant, draft ownership, contact, capability hashes        | Private Installation-scoped operational records; unsigned Notion Browser Capability hashes retain their current storage contract                                                  |
| Verified Votes, Follows, consent, read state, delivery intents           | Private D1 records; public output contains only explicitly eligible aggregate support                                                                                             |
| Portal Comments                                                          | Comment adapter: existing native Notion path or explicitly marked App-created GitHub issue comments; private D1 attribution/mappings; arbitrary engineering comments are excluded |
| Attachments                                                              | Private R2 bytes and private operational associations; publication checked on every download                                                                                      |
| Operations, binding credentials, receipts, failures, source checkpoints  | Private operational records, never public issue metadata or public configuration                                                                                                  |
| Public observed history                                                  | Allowlisted projection of eligible records, separate from private actor attribution and provider discussion                                                                       |

Every operational key includes or is constrained by authenticated Installation identity. A request cannot select another Installation by submitting an ID. Preserve the existing issuer/subject trust pair; changing provider does not change verified identity. Changing an issuer or crossing Product Teams requires an explicit verified mapping, and email equality is never identity evidence. Existing operational rows are migrated without manufacturing ownership for old Posts.

New signed-in submissions bind ownership from the verified server session, independently of submitted Device Profile fields. Browser-held authority may explicitly link an unsigned Draft Post to the current Verified Participant; neither email matching nor possession of a public URL suffices. The edit/withdraw rule stays New and unpublished even for verified owners. Public and owner reads use separate projections/cache paths; owner responses are private and `no-store`.

## GitHub public content and Comments

Define one exact versioned section in the issue body, delimited by `<!-- feedbax:public:v1 -->` and `<!-- /feedbax:public -->`, containing a validated JSON object with `slug`, `title`, `description`, `type`, optional `teamResponse`, and optional `releaseNotesUrl`. Reject missing/duplicate sections, unsupported versions, invalid field types/limits, slug changes, and unsafe links. Never fall back to rendering the entire issue body. Repository issue titles are engineering metadata; the explicit title field controls the portal. A public repository exposes its issue title/body immediately, regardless of portal publication.

New issues include only the public-content section and safe workflow metadata. Contact details, capability hashes, ownership, operation keys, idempotency keys, binding credentials, or private R2 review links never enter issues, including private issues that could later become public. D1 holds private fields. An opaque public slug can identify approved content, but is never proof of authority.

Portal Comments have a separate versioned structured representation, a durable D1 mapping, and a verified App author. Merely copying a marker into an engineering comment cannot publish it. Replies preserve thread identity and original Participant attribution without impersonating a GitHub account. Native GitHub engineering comments stay private from the portal by default. New engineering-reply publication tools are deferred. An explicit native edit of approved Post content/Team Response remains a supported workflow; feed responses present team contributions as Product Team.

Public projections explicitly allow only Post content, public slug/timestamps/type/status, safe team response/release link, eligible support counts, approved Comments, and safe attachment references. Provider IDs, raw issue/PR URLs and payloads, contacts, actors, sessions, capabilities, and diagnostics are omitted. Public GitHub issue/PR links require an explicit configuration opt-in and a current public-repository check. A private repository always suppresses these links regardless of configuration. Disabling publication suppresses history, Comments, images, and new deliveries as well as the Post.

## Workflow and account matrix

Issues-only is the default: exactly one of the six `feedbax:*` status labels is authoritative; `feedbax:published` is separate. No status label or conflicting status labels produce diagnostics and preserve the last valid status, not an inferred Shipped/Closed decision. Removing `feedbax:published` revokes publication even if status is invalid. Issue closure alone is not a delivered/rejected decision. Explicit opt-in automatic publication applies only to public feedback repositories and never overrides removal/quarantine.

Project mode uses one configured Project and its stable single-select field/option IDs as the sole status authority. Status labels cease to be authoritative. Missing options, removed membership/fields/Project, permission loss, and native automation conflicts produce diagnostics and reconciliation; never silently fall back to labels mid-operation. A deliberate reconfiguration can select Issues-only. Retain last valid status on schema drift, while handling visibility revocation separately.

| Account/resource                                                             | 0.2.2 implementation target                    | Credentials and acceptance                                                                                                                        |
| ---------------------------------------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Personal GitHub account, public/private Issues                               | Issues-only                                    | Installation-scoped App access to selected repository; real public/private setup required                                                         |
| Organization, public/private Issues                                          | Issues-only                                    | Approved repository permissions and installation access; real setup required                                                                      |
| Organization-owned Project with selected repository in the same organization | Optional Project candidate                     | Organization Projects permission, repository access and successful field/item query/mutation probes; live evidence required before support claims |
| Personal/user-owned Project                                                  | Issues-only fallback                           | No user-token/PAT path introduced in 0.2.2; reject Project mode with an actionable Issues-only choice                                             |
| Cross-owner Project/repository or enterprise-server API host                 | Issues-only on supported GitHub.com repository | Not a supported Project pairing; no inferred cross-owner access or untested Enterprise Server compatibility                                       |

This is a product support matrix, not a claim that GitHub cannot support other combinations. GitHub documents organization Project endpoints with installation tokens and organization Projects permission, while its user Project REST endpoints do not accept installation tokens. The GraphQL guide separately describes installation-token access; setup must probe the exact mutations used rather than infer write access from a successful read. Sources checked 2026-10-15: [Project REST permissions](https://docs.github.com/en/rest/projects/projects), [GraphQL Project management](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects), [App permission categories](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app).

PR automation is disabled by default. When enabled, only authenticated implementation links to allowed repositories can advance eligible New/Reviewing/Planned Posts to In Progress. Arbitrary mentions, unmerged closure, and merge do not imply Shipped or Closed. Manual provider decisions and native Project authority win; a manually selected status remains until an explicit new eligibility decision. Multiple PRs never imply all work shipped; reopening a PR does not reopen a manually Shipped/Closed Post.

## App pairing, transport, and recovery

The official and team-owned App use the same Core implementation. Only the integration service holds the App key. Request Issues read/write and metadata access for feedback; PR read access applies only to explicitly linked development repositories; Project permissions are conditional on the supported mode. Do not request code contents/diffs merely to discover implementation links. Validate actual permissions/account/resource ownership during setup.

Pairing is a short-lived, one-use exchange initiated with Deployer-controlled portal credentials and bound to the exact HTTPS origin. Complete an authenticated GitHub authorization/installation callback, verify the selected repository belongs to the installed accessible resources, and challenge the destination portal before activating a binding. A callback Installation ID, state string, repository name or destination URL alone is insufficient. Reject cross-origin substitutions, callback replays, unsupported destinations and redirects to unverified hosts. Prevent loopback/private-network/metadata endpoint delivery, including through DNS changes. Self-hosted services explicitly configure trusted portal destinations rather than accepting arbitrary URLs.

After pairing, portal-to-service requests and service-to-portal deliveries use separate directional, Installation-scoped secrets, timestamped body authentication, bounded clock skew, nonce/operation deduplication and key rotation. The service derives binding authority from authentication and looks up the permitted repository/Project server-side. It never accepts a resource ID as permission. Binding revocation invalidates both directions and queued work.

Validate GitHub webhook HMAC over the raw, bounded request body before parsing. Persist a receipt and queued work before acknowledging success; if durability fails, return failure. Use delivery ID plus App identity for ingress deduplication, and binding/resource identity for downstream work. Durable D1 state contains operation identity, desired revision, current phase, attempt count, lease/fencing token, next attempt, safe failure code, and timestamps. Queue messages contain opaque work references where possible. Reordered/retried events trigger current authoritative reads rather than replaying stale payload projections.

Reserve stable IDs/slugs and operation keys before external creation. Never blindly retry an ambiguous issue/comment create after a timeout: retain the uncertain operation, reconcile App-created public-content identities and mappings, and stop for diagnosis if uniqueness cannot be proven. D1 transactions commit local records/checkpoints only; they do not make GitHub writes atomic. Compare revisions and fence stale completions; record partial progress rather than rolling back an external write by assumption. Tests must cover the crash after provider success but before the mapping commit.

Retries are bounded, honor provider rate-limit timing and reschedule long waits rather than blocking a Worker. Begin with five-minute authoritative polling, stale warning after 15 minutes, maximum ten records per standard pass or one record per small-mode work item, and five delivery attempts with jittered backoff capped at one hour. Configuration may lower per-run work or change intervals/thresholds with explicit validation. Persist next cursors, fairness and last successful check so a large backlog cannot starve later records. These are configuration defaults to validate in real Workers, not capacity guarantees.

Delete successful raw payloads after all required durable downstream work is safely represented. Expire failed raw payloads within seven days of receipt; retain only sanitized codes/counts/times for up to 30 days. Apply the limit to service-owned queue/failure-store copies, backups, logs and portal delivery copies. Expiry schedules authoritative reconciliation; it does not discard deduplication tombstones or cause blind re-creation. Deduplication and stable external mapping records contain no raw payload and persist as long as needed to avoid replaying historical effects.

Explicit unpublication/deletion/repository removal/App uninstall or suspension revokes visibility and stops writes/deliveries immediately when observed. Permission loss fails closed for affected content and does not delete source records. A last valid status is safe to retain only when publication/authorization remains valid. Invalidate caches and deny attachments on revocation; do not serve a stale public projection through the baseline stale-on-error policy after known revocation. A missed event is bounded by the configured authoritative check interval, not an instant revocation promise. Release acceptance measures that delay.

## Participant views, history, merge, and moderation

My feedback is a private Connected Profile surface with Submitted, Supported and Following filters, bounded pagination and loading/empty/error states. Ownership derives only from server-verified identity or a confirmed Browser Capability claim. A Participant sees their own pending content with safe lifecycle information; another Participant receives ordinary unavailable behavior. Withdrawn/removed records remain understandable without revealing provider records. Unsupported merge execution does not prevent stable canonical alias reads.

Observed History separates provider event time from observation time. New public status observations contain no private text; explicit public updates require approved content. Publishing a Post does not backfill private historical events. Store private actor attribution separately and display Product Team. Shipped links point to Published Changelog Entries or safe HTTPS/root-relative release notes. Reject unsafe schemes and unpublished internal targets. Deduplicate history and notification intents by stable logical event, including repeated transitions, polling, webhook retries and historical imports.

The merge contract rejects self/cyclic/cross-Installation merges and retains original immutable URLs as aliases. Resolve only to visible canonical content; unavailable/private targets expose no details. Union verified Votes and Follows by trusted identity while preserving consent/read/delivery state and sending no historical Notifications. Preserve original Comment attribution/time/source context and attachment authorization through durable associations; do not delete provider history or copy private source attachments into public access merely by merging. Record per-source legacy unverified counts and their potentially overlapping sum separately from verified support. Merge execution remains deferred without a safe native authorized workflow.

Restrictions, when implemented, apply to explicitly scoped future submission/Comment/Vote actions; preserve read access, prior Votes and independent Follow/consent state unless separately moderated. Trusted submissions cannot accidentally bypass subject-based restrictions: verified-subject attribution requires a server-validated assertion; subjectless trusted submissions remain explicitly Deployer-authorized service intake, unverified and subject to submission limits/moderation. No email/name matching creates a restriction identity. Anonymous controls are best-effort only.

Report review/restriction/batch execution is deferred without safe native private workflows. Reports must never place reporter/contact details in a public issue, and report counts cannot auto-remove content. Future batch actions require preview, bounded work, an authorized action record and resumable partial results; use reversible quarantine where possible. Existing native publication/removal remains supported, with image/cache invalidation and pending-delivery suppression. No new Team Member runtime authority is introduced by these contracts.

## Portable archive, upgrade, restore, and migration

Archive format v1 consists of a JSON manifest and content/object files with schema version, origin Installation/Product Team/issuer identities, created time, record/file counts, SHA-256 checksums, public/private classifications and required credential dependencies. Archive entities include Posts/content/timestamps/slugs/provider references, Comment/thread/source context, ownership/attribution, verified and legacy support, Follows/consent/read state, delivery deduplication/checkpoints, aliases, moderation/history, redacted configuration and R2 bytes/associations. Preserve unsupported fields as private metadata or reject before writing. CSV rows never manufacture verified Votes or identities from names, addresses or counts.

Portable archives exclude credentials, active sessions, replay nonces and capability secrets/hashes. Restore invalidates unsigned draft capabilities and lists reconnect/rotation requirements. Recoverable provider content is required for disaster recovery; provider pointers alone are insufficient. Private archives require encryption with a caller-supplied recovery key or an explicit protected local destination with restrictive permissions. Integrity/schema/size/path validation and a dry-run manifest precede writes; reject traversal, corrupted/incomplete files, incompatible schemas and invalid trust mappings.

Upgrade released 0.2.1 generated Installations using a versioned source baseline, local source and target source. A manifest of target generated files includes baseline hashes; compare all three before applying changes. A pre-baseline 0.2.1 Installation derives its baseline from the exact published creator version, never from current main. Preserve independent edits and stop on conflicts. Separate source, configuration, D1, secret reconnect and deployment stages with durable resumable checkpoints and a rollback compatibility statement for each migration. No source replacement or schema destruction is automatic without a verified recovery path.

Restore initially creates an isolated, disabled Installation, verifies content/object integrity and suppresses all historical notification/email work. Preserve deduplication state without creating new delivery intents. Reconnect identity and provider credentials explicitly; a restored clone cannot activate the original binding while the original writer remains active. Cross-Product-Team imports keep mismatched subjects unverified and do not transfer consent. Enabling a clone or changing authority is an explicit Deployer cutover.

Both provider migration directions use preflight, snapshot, preview, a durable write fence, resumable copy, count/checksum and sampled visibility verification, authority switch, cache invalidation and resume. Queue or reject writes while fenced; never run two authoritative provider writers. Preserve the rollback point until verification succeeds. Stable Feedbax identity survives while provider mappings change; Comments retain source attribution and are not impersonated as original provider users. Show unsupported content/loss before confirmation and reject unrepresentable required data. Imports and migrations do not notify Participants about historical activity.
